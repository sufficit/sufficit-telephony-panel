# Idle extension prefix correction

## Report and cause
The screenshot showed Hugo Deco (Office), google-voip, with the generic queue/trunk
mapping warning after 0.12.1. The previous fix still resolved endpoint candidates
only from active call channels. Continuous monitoring must also work while idle.
Google's real gRPC snapshot contained `SIP/0000006007`, kind peer, Registered,
empty Account, and no active channel for the user's 00000060xx extensions.
Peer state-transition times also legitimately exceeded the call freshness window.

## Changes
- Resolve a PEER's literal SIP/PJSIP identity from the connected live projection
  even when no call is active. Preserve the exact anchored portal key comparison
  and terminating channel delimiter; no regex, label or queue-name authorization.
- Use the selected context when the peer event has no account. Re-query the scoped
  authorized portal PEER catalogue at submission. Without a selected context,
  require an explicit unambiguous observed account rather than guessing ownership.
- Peer Updated is a state-change timestamp, not a heartbeat. Stable peers in the
  connected projection remain usable. Disconnected streams, future timestamps,
  foreign accounts and remembered-only cards cannot grant the target.
- Share this evidence check between UI candidate resolution and server submission.
  Exact-channel listening retains its existing fresh active-channel requirement.
- PEER failures now have a specific EN/PT endpoint/context/connection explanation,
  not the queue/trunk mapping warning. The SUI layout and one-shot auto-listen flow
  remain unchanged. Trunks and queues still require exclusive protected mappings.
- Software-development and sufficit-frontend guided the focused correction and
  existing SUI/browser validation.
